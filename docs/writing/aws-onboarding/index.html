Guardrails, Not Tutorials

Designing an agent skill that gets a beginner onto AWS — and back off it again

Matt Duke Dallas, TX 2026 github.com/MatthewDuke1/aws-onboarding MIT

Summary

Every AWS tool built for an AI assistant starts after aws configure already works, and stops at a running stack. Those are exactly the two ends a first-time user needs most: getting to working credentials without leaking one, and getting back to zero without a surprise bill.

aws-onboarding is a Claude Agent Skill that fills both. It is a 212-line instruction file, eight on-demand reference guides, one Python preflight script, and a behavioral test suite. The interesting part is not the AWS content — Claude already knows AWS. It is the enforcement model: the one rule that must never bend is implemented as an exit code rather than a paragraph.

01The gap

Look at what already exists.

AWS's own Deploy on AWS plugin documents its prerequisites plainly: an account, working credentials, the CLI installed. It does not cover account creation, IAM, MFA, billing alarms, or teardown. HashiCorp's Terraform agent skills are written for people who build Terraform providers for a living. The dozens of community AWS skill packs are service references — DynamoDB, IAM, CloudWatch — aimed at someone who already has a console open.

So the coverage looks like this:

Both uncovered ends fail the same way, and both fail silently. A beginner who half-configures the CLI gets commands that appear to succeed while hitting the wrong account or region. A beginner who finishes a tutorial gets a NAT gateway they will discover on a credit card statement fourteen months later.

02The reframe: the constraint is trust, not knowledge

The obvious way to build this skill is to write a very good AWS tutorial and hand it to the model.

That would be wasted effort. Claude can already explain IAM, or Terraform state, or what a stack is, on demand and better than most tutorials — because it can answer the follow-up question. Knowledge is not scarce here.

What stops people is trust. Three specific fears, all rational:

  • Cost you cannot see coming. The bill arrives a month after the mistake.
  • Changes you cannot reverse. No undo button, and the delete path is genuinely harder than the create path.
  • A console that never tells you what you already own. Fifty services, thirty regions, no single view of "what is running and what is it costing me."

The useful thing to build is not another explanation. It is a set of guardrails that make the fears unfounded, and then say so.

This is the same reframe that shows up in enterprise deployment work, incidentally. The blocker on a platform rollout is almost never that the customer does not understand the product. It is that nobody has made the first irreversible step safe to take.

03The non-negotiables

Eight rules sit at the top of SKILL.md and explicitly override both convenience and the user's own requests to skip ahead. The important ones:

  • A budget exists before any billable resource does. No exceptions. A beginner's worst outcome is a surprise bill, not a slow tutorial. Setting a zero-spend budget takes about two minutes and is the difference between a $3 mistake and a $300 one.
  • Never ask for, accept, or echo a secret. No root passwords, no access key IDs, no MFA codes typed into a chat. If the user pastes one anyway, the skill tells them to rotate it immediately and does not repeat it back.
  • Prefer IAM Identity Center over long-lived access keys. Static keys sitting in ~/.aws/credentials are the single most common way beginners get compromised. Access keys are a documented fallback, not the default, and the skill says why when it falls back.
  • Never create without a teardown path. Every create step names how to undo it, in the same message. Not in a section at the end.
  • State cost before creating. A number, and what drives it. "Roughly $0 while idle, about $18/month if you leave the NAT gateway running" is useful. "Costs vary" is not.
  • One concept at a time. Do not explain VPCs, IAM, and state files in one message.

04Architecture

aws-onboarding/
├── SKILL.md          212 lines: rules, 8-step workflow, routing table
├── reference/        8 guides, loaded only when relevant
├── scripts/
│   └── preflight.py  the deterministic gate
└── EVALS.md          behavioral test suite

SKILL.md is a router, not an encyclopedia. It holds the rules, the eight-step workflow, and a table pointing at reference files. The eight guides — account setup, credentials, guardrails, tool choice, CloudFormation, Terraform, teardown, troubleshooting — are only read when the conversation actually needs them.

That is progressive disclosure, and it is the difference between a skill you leave installed and one you uninstall. Having this one installed costs almost nothing in context until you ask a question that pulls a guide in.

The workflow is eight steps, and Claude reproduces the checklist in its replies so the user can see where they are: 

- [ ] Step 0: Work out where they actually are
- [ ] Step 1: Account exists, root is locked down
- [ ] Step 2: Sign-in works from the command line
- [ ] Step 3: Spend guardrails in place
- [ ] Step 4: Pick CloudFormation or Terraform
- [ ] Step 5: Deploy the smallest real thing
- [ ] Step 6: Change it, and watch the change apply
- [ ] Step 7: Tear it down

Three of those deserve a note.

Step 0 asks whether an employer owns the account. In a company account the user probably cannot create an IAM user or a budget, and the correct answer becomes "here is the request to send your platform team, naming the account, region, and permissions." Skipping this question walks someone straight into a permissions wall and leaves them thinking they broke something.

Step 5 deploys something real, not hello world. An S3 static site or a Lambda on a schedule — something they would plausibly keep, genuinely free at rest. The template gets written with them, one line of explanation per block as it appears, rather than pasted in as a 200-line starting point.

Step 7 is the whole point. A beginner who has never destroyed a stack does not trust themselves to experiment. Teardown is not cleanup at the end of a tutorial; it is the step that makes every previous step usable.

05Why the guardrail is an exit code

The budget rule is the one that has to hold under pressure, because the moment it matters is exactly the moment the user is impatient. "Skip the setup stuff, just give me the Terraform" is the realistic input.

A model can be talked out of a checklist. Instruction text is a strong prior, not a constraint — enough conversational pressure, or enough distance from the top of the context window, and it bends.

So the check is not prose. Before any deploy:

python scripts/preflight.py

It verifies the CLI is installed, credentials resolve, a region is set, a budget exists, and the caller is not root. It prints a numbered list of problems with the exact fix for each, and exits non-zero if anything is wrong.

A model can be reasoned past a paragraph. It cannot be reasoned past a return value.

That is the design decision worth stealing. Where a rule genuinely must not bend, move it out of the prompt and into code the model executes and cannot argue with. Everything else in the skill is guidance; this one thing is a gate.

The script needs Python 3.8+ and no third-party packages, because a beginner who has to pip install something to run the safety check will not run the safety check.

06Evaluation

Anthropic's authoring guidance recommends writing evaluations before writing extensive documentation. EVALS.md holds five scenarios, each run against a fresh Claude instance with a baseline established without the skill first — otherwise you cannot tell whether the skill is doing anything.

ScenarioWhat it tests
Absolute beginner, no accountDoes it ask before instructing? Budget before resources? Teardown at the end?
The impatient userDo the non-negotiables survive pressure — without flipping to a refusal loop?
Employer-owned accountDoes it recognize a permissions wall instead of suggesting AdministratorAccess?
Teardown after the factGiven "$40/month and I don't know why," does it reach for NAT gateway and RDS first?
Tool choiceDoes it recommend, or produce a balanced-but-useless comparison?

The impatient-user case is the one that matters most, and it has two failure modes, not one. Silently skipping the budget is the obvious failure. Refusing to help until every step is complete is the other, and it is just as bad — the skill should state the specific risk once and then proceed if the user insists again.

Across all five, the watch list is: budget skipped under time pressure, secrets appearing in the transcript, teardown treated as optional, jargon used before it is defined, reference files never opened, and over-explaining on the larger models. When something fails, the fix is to tighten the wording in SKILL.md, not to add more of it.

07Limitations

Worth stating plainly.

  • Claude Code only. The skill shells out to the AWS CLI, so it does not work uploaded to the Claude API, which runs skills without network access.
  • The evals are run by hand. There is no runner. That is a real gap.
  • It does not make AWS as easy as Vercel. It is not. It makes it reachable, which is a different and smaller claim.
  • The preflight verifies configuration, not intent. It confirms a budget exists. It cannot confirm the user understood what they are about to create.

08Why build it at all

Default deployments have consolidated onto Vercel, Netlify, and the other fully managed platforms, and the reason was always the same: AWS cost more in operator attention than a small project could justify.

That tradeoff was real. It is now mostly gone. With a capable model sitting next to you, AWS resource management is no longer the tax it was — the knowledge gap that made managed platforms the rational default has largely closed. What remains is the trust gap, and a trust gap is a tooling problem.

Which is the general point. As models absorb the explanation half of technical onboarding, the leverage moves to the parts that are not explanation: irreversibility, cost exposure, and the confidence to take a first step. Those are built in code, not in prose.
